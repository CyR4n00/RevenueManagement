# レベナビ パイロット運用点検（2026年8月30日）

## 結論

画面、認証、契約、保存済みデータの表示はパイロット利用できる状態です。一方、価格取得は「動くこと」ではなく「毎日安定して正しいこと」を確認する段階です。営業先へ完成版として案内する前に、7日連続取得とOTA画面との照合を終える必要があります。

## 今回見つかった重要事項

### 対応済み：画面表示による取得枠の消費

以前は、概要画面を開く・日付を変える・表示期間を変える操作でも、外部取得が実行されていました。このため、顧客が見るだけでApifyの日次実行枠を使い、夜の定期取得が止まる可能性がありました。

修正後は、通常画面では保存済みデータだけを読みます。取得は午前9時と午後6時の定期処理に分離され、顧客がログアウトしていても動きます。

### 対応済み：失敗した定期処理が成功表示になる問題

施設ごとの失敗を内部で処理した結果、Google Cloud上ではジョブ全体が成功に見える場合がありました。修正後は、対象施設を最後まで処理したうえで、1件でも失敗すればジョブを失敗として終了します。

### 対応済み：自動再試行による取得枠の重複消費

失敗時の自動再試行を0回に変更しました。現在の1日2回という取得設計では、無条件の再試行が本来の夕方分を消費するためです。

### 対応済み：顧客が取得状況を判断できない問題

概要画面に次を表示します。

- 最終成功時刻
- 直近7日間の成功回数と失敗回数
- 保存済みの宿泊日数
- 自動取得予定時刻
- 正常・要確認・未開始の状態

「表示を更新」は保存済みデータを読み直すだけで、Apifyの利用量を増やしません。

### 対応済み：外部サービスの詳細エラーに秘密情報が残る危険

顧客画面とログには、外部サービスが返した認証ヘッダーなどの詳細を連結しないようにしました。運営用には原因を特定できる範囲の安全なエラーだけを残します。

## パイロット開始前に残る確認

### 最優先

1. ApifyのAPIトークンを再発行し、Google Secret Managerの値を更新する。
2. 午前9時・午後6時の取得が7日間連続で成功することを確認する。
3. 楽天トラベル・じゃらんの画面と、レベナビの価格、部屋なし、残りわずかを日付ごとに照合する。
4. 90日先まで取得できる施設と、取得できない施設を記録する。

APIトークンは過去の外部サービス例外に含まれてCloud Loggingへ記録された可能性があります。現在の値は今後使い続けず、必ずローテーションします。

### メール

1. 所有ドメインまたは送信用サブドメインをResendで認証する。
2. Supabase AuthへResend SMTPを設定する。
3. 登録確認、メールリンク、パスワード再設定の日本語テンプレートを設定する。
4. アプリ通知用のResend APIキーと送信元アドレスをSecret Managerへ設定する。
5. Gmail、Outlookなど複数の宛先で受信、迷惑メール、リンク遷移を確認する。

手順は [メール設定手順](./EMAIL_SETUP.md) を使用します。

### 契約・運用

1. 振込顧客の利用開始・停止・期限切れを実際の運営画面で確認する。
2. Stripeを使う場合は本番本人確認、本番Price ID、本番Webhookを別途設定する。
3. 障害時の問い合わせ先と、一次回答を行う担当者を決める。

## 合格基準

- 7日間で予定した14回の定期処理が実行され、失敗があれば画面とCloud Run Jobの両方で分かる。
- 登録した競合施設ごとに90日先までの取得結果または明確な未取得理由がある。
- 抽出した価格が、同じ日、同じ人数、同じ条件のOTA画面と一致する。
- 「未取得」を0円、「部屋なし」を満室率として誤表示しない。
- 顧客が画面を開かなくても取得される。
- 他の顧客の施設や価格を閲覧できない。
- 登録確認、ログイン、パスワード再設定の各メールが届き、公開URLへ戻れる。
